# Product Requirements Document: Custom Risk

**Version:** 3.2  
**Date:** 2026-05-04  

---

## 1. Overview

**Custom Risk** is the working product name for a configurable risk management web application.

 The final product name will be revisited before branding, marketing, or public release.

Custom Risk is a flexible risk register platform where each register can define its own fields, scoring model, risk matrix, validation rules, review workflow, response action model, notifications, permissions, and import/export behaviour.

The product is designed for end users who are not risk management specialists. It should make it easy for users to understand what they own, what needs review, what actions they are responsible for, and what needs attention, while giving administrators a powerful configuration model behind the scenes.

## 2. Product Principles

1. **Transparency and ownership:** users should clearly see the risks and actions they own.
2. **Low-friction risk review:** risk owners should be able to review risks quickly with clear attestation and audit evidence.
3. **Flexible configuration:** registers should support different methodologies without code changes.
4. **Auditability:** important changes must be traceable by who, when, what, and where.
5. **Self-managing process:** reminders, review rules, validation, dashboards, and ownership views should reduce manual chasing by risk leaders.
6. **Usability first:** configuration can be powerful, but day-to-day end-user workflows must remain simple.

## 3. Core Concepts

### 3.1 Register

A **Register** is a configurable risk register. The application must support multiple registers.

Each register may have its own configuration or be created from a versioned template. Register configuration includes fields, formulas, scoring, validation, reviews, notifications, permissions, and response action behaviour.

### 3.2 Risk

A **Risk** is a full risk register entry. The term Risk refers to the whole record, not only the score.

### 3.3 Risk Score and Risk Level

* **Risk Score** is the numeric/mathematical result of the configured calculation, such as `Likelihood * Impact`.
* **Risk Level** is the qualitative value assigned from the risk matrix, such as Low, Medium, High, or Critical.

Where inherent and residual risk are enabled, the app uses:

* Inherent Risk Score
* Inherent Risk Level
* Residual Risk Score
* Residual Risk Level

### 3.4 Risk Response Strategy

**Risk Response Strategy** is the broad response category for a risk. Default values are:

* Accept
* Mitigate
* Transfer
* Avoid

Register Admins may configure these values. If the strategy is **Accept**, the register may allow no Risk Response Action to be required.

### 3.5 Risk Response Action

A **Risk Response Action** is a concrete action, treatment, control, task, or response linked to one or more risks.

Risk Response Actions can be implemented in two modes:

1. **Simple field mode:** a simple field on the risk.
2. **Child record mode:** separate records linked to risks.

New registers default to simple field mode. Register Admins can switch to child record mode where they need separately owned, trackable, reusable actions.

## 4. Mandatory Risk Capabilities

Every register must support the following logical capabilities. These are not always literal fields because some capabilities change depending on configuration.

1. Risk ID
2. Risk Title
3. Risk Description
4. Risk scoring inputs, such as Likelihood and Impact
5. Risk Score
6. Risk Level
7. Risk Owner
8. Created Date
9. State
10. Risk Response Strategy
11. Risk Response Action capability, where applicable

### 4.1 Risk ID

Each risk has a displayed Risk ID.

Risk ID requirements:

* System-generated by default.
* Unique within a register.
* Configurable prefix or format per register.
* Import can preserve existing IDs if no duplicate exists.
* Duplicate imported IDs block import unless explicit update/merge mode is selected.
* The system also stores an immutable internal UUID for each risk.

### 4.2 Created Date and System Metadata

**Created Date** represents the business/original creation date of the risk. It is system-generated by default but may be overridden by authorised users.

Override permissions:

* System Admins can override Created Date.
* Register Admins can override Created Date.
* Risk Owners can override Created Date only if the register setting **Allow Risk Owners to override Created Date** is enabled. Default is No.

The system must also maintain immutable metadata separate from Created Date:

* System Created At
* System Created By
* System Updated At
* System Updated By

All Created Date overrides must be audited.

### 4.3 State

Every risk has a State field with default values:

* Draft
* Open
* Closed

Closed risks are excluded by default from operational views, dashboards, and standard reports, but can be included by authorised users through filters or report settings.

Hard delete is restricted to System Admins and is for mistakes/errors only. Hard deletion must create an audit log entry and preserve a full last-known snapshot.

## 5. Custom Fields

Register Admins can add custom fields to registers. Supported field types:

1. **Text:** short single-line text.
2. **Multi-line text:** long-form text.
3. **Boolean:** true/false.
4. **Number:** numeric field with configurable precision.
5. **Calculated field:** formula-derived value; not directly editable by normal users.
6. **Person Picker:** email-address based person field.
7. **Date:** date field with configurable display format.
8. **Drop Down:** single-select field with configured values.

### 5.1 Person Picker

Person Picker fields are based on email address.

Behaviour:

* Users enter or search for an email address.
* Existing local users appear as autocomplete values.
* External-auth users appear once known through prior login, provisioning, directory synchronisation, or similar mechanisms.
* SAML alone does not guarantee live directory search.
* If no user exists, the full email address can still be entered.
* If that email later becomes associated with a user account, the value inherently links to that user.

This applies to Risk Owner, Risk Response Owner, custom person fields, notification recipients, and similar fields.

### 5.2 Field Validation

For each applicable field, Register Admins can configure null/empty behaviour:

* Allow
* Warn on save
* Block save

Validation warnings and errors should be visible in the UI at field, row, register, and dashboard levels where appropriate.

### 5.3 Field Visibility

Fields should support visibility controls where required by permissions. At minimum, default and custom risk fields must support:

**Visible to Risk Response Owners: Yes/No**

This controls what parent-risk context is visible to a Risk Response Owner who only has access because they own a linked action.

This visibility rule must apply consistently across detail views, linked previews, tables, search results, exports, notifications, and future APIs.

## 6. Field and Configuration Lifecycle

Register configuration changes should protect existing data.

Rules:

* Field deletion should be soft deletion/deactivation by default once data exists.
* Destructive deletion should be restricted, confirmed, and audited.
* Field type changes may require migration or remapping.
* Dropdown values used by existing records should be deactivated rather than deleted.
* Existing records retain historical dropdown values.
* Users cannot select deactivated dropdown values for new updates unless reactivated.
* Formula changes require impact analysis and recalculation where applicable.

Configuration edits may be made in draft. A new configuration version is created when changes are published. Draft changes do not affect the live register until published.

Publishing a configuration version should run an impact analysis showing affected records, fields, validation changes, formula recalculations, required migrations, possible data loss, and response action mode changes.

## 7. Risk Scoring and Matrix

### 7.1 Likelihood and Impact

Register Admins define Likelihood and Impact values, including display name, numeric value, and order.

The same configured Likelihood scale is used for both inherent and residual likelihood where inherent/residual mode is enabled. The same applies to Impact.

### 7.2 Risk Score Formula

The default Risk Score formula is:

`Likelihood * Impact`

Register Admins can configure custom formulas. Initial formula support should be limited to:

* Numeric fields
* Numeric lookup values
* Constants
* Arithmetic operators: `+`, `-`, `*`, `/`
* Parentheses

Boolean fields may be treated as true/false or 1/0 only if explicitly supported. Text, date, person, and freeform dropdown labels are not valid numeric inputs unless mapped to numeric values.

For registers using inherent and residual risk, the Register Admin can choose:

* Use the same formula for inherent and residual risk.
* Use separate formulas.

### 7.3 Risk Matrix and Risk Levels

The Risk Matrix is generated from all Likelihood and Impact permutations.

The matrix is used to assign Risk Levels, such as Low, Medium, High, or Critical, to each Likelihood/Impact permutation.

Register Admins define the available Risk Levels once, then assign a level to each matrix permutation.

Matrix-based Risk Level assignment is only guaranteed where the configured score formula can be evaluated for each Likelihood/Impact permutation.

## 8. Inherent and Residual Risk

Each register has a setting:

**Use Inherent and Residual Risk Fields: Yes/No**

When disabled, the register uses standard scoring inputs and outputs:

* Likelihood
* Impact
* Risk Score
* Risk Level

When enabled, the register uses:

* Inherent Likelihood
* Inherent Impact
* Inherent Risk Score
* Inherent Risk Level
* Residual Likelihood
* Residual Impact
* Residual Risk Score
* Residual Risk Level

## 9. Risk Response Actions

### 9.1 Modes

Risk Response Action behaviour is configured per register.

**Simple field mode:** the action is stored as a simple field on the risk.

**Child record mode:** actions are separate records linked to risks.

Risk Response Actions in child record mode are always scoped to a single register and are never cross-register.

### 9.2 Child Record Defaults

A child Risk Response Action has at least:

* Risk Response: multi-line text
* Status: configurable dropdown

Default status values should provide a useful starting point, for example:

* Planned
* In Progress
* Implemented
* Deferred
* Cancelled

Register Admins can configure the available status values per register, including names, display order, active/inactive state, and whether each status represents an active, completed, paused, cancelled, or failed response state.

The status field should be visible anywhere linked Risk Response Actions are shown, including:

* the Risk detail screen;
* Risk Response / My Actions views;
* linked action previews;
* relevant dashboards and reports;
* exports where the user has permission to see the action data.

On the Risk detail screen, linked Risk Response Actions should show their current status clearly so that the Risk Owner can understand whether planned controls are still pending, partially underway, implemented, cancelled, or otherwise ineffective. This status context should help the Risk Owner make an informed residual risk assessment, but status alone must not automatically change the risk's residual Likelihood, Impact, Risk Score, or Risk Level.

Status changes must be audited as Risk Response Action field changes and should be visible in Risk Response audit history. Where a status change affects risk-level context, the linked Risk audit/history view should also show that a linked action changed status.

Register Admins can add fields such as Risk Response Owner, Due Date, Priority, Completion Date, Evidence, Category, Affects, and Notes.

### 9.3 Linking Rules

Within the same register:

* One risk can have multiple Risk Response Actions.
* One Risk Response Action can be linked to multiple risks.
* Risk Owners can add new actions to risks they own.
* Risk Owners can link existing actions to risks they own where they have permission to see or link the action.
* Risk Owners can unlink actions from risks they own where permitted by register configuration.

### 9.4 Deletion and Orphan Handling

Hard-deleting a risk removes the risk and its links to Risk Response Actions.

Linked Risk Response Actions are not automatically deleted if they are linked to other risks.

If a linked Risk Response Action would become orphaned because the deleted risk is its only linked risk, the delete flow should offer an option to delete the related orphaned action as part of the same administrative operation.

Deleted risks and deleted Risk Response Actions must be captured in audit logs with last-known snapshots.

### 9.5 Switching Modes

Switching from simple field mode to child record mode requires a migration step. Existing simple response values can optionally be converted into one child Risk Response Action per risk.

Switching from child record mode back to simple field mode should be restricted or require explicit migration/export/archive because child records may contain richer data, ownership, audit history, and many-to-many links.

## 10. Reviews

### 10.1 Risk Reviews

Risk reviews are configurable per register using:

**Enable Risk Reviews: Yes/No**

When enabled, users with permission can click **Review Risk**.

The review flow must:

1. Show configurable attestation text.
2. Support review comments as Disabled, Optional, or Mandatory. Default is Optional.
3. Record reviewer.
4. Record timestamp.
5. Recalculate the next review date.
6. Create audit and review history entries.

### 10.2 Risk Response Reviews

Register Admins can separately enable reviews for Risk Response Actions using:

**Enable Risk Response Reviews: Yes/No**

Risk Response reviews follow the same model as risk reviews.

### 10.3 Review Frequency Rules

Review frequency is configured using rules based on field values.

Examples:

* High residual risk reviewed every X months.
* Residual Risk Acceptable = true reviewed every Y months.
* Residual Risk Acceptable = false reviewed according to residual risk level.

Next Review Date is normally calculated from Last Reviewed Date, or Created Date if never reviewed.

Edits should trigger recalculation of the applicable review frequency where relevant fields change. If the rule changes, the Next Review Date is recalculated using the latest applicable frequency and Last Reviewed Date, or Created Date if never reviewed.

### 10.4 Review History

Each risk and Risk Response Action should retain review history including:

* Reviewer
* Timestamp
* Comments, where enabled
* Attestation text or attestation version
* Calculated next review date
* Review outcome/status, where applicable

Review events must also be reflected in audit logs.

## 11. Notifications

Notifications are configurable per register and should support risk reviews and Risk Response Action reviews.

Reminder settings include:

* Notify when due within X days.
* Repeat every Y days.
* X may be negative to notify only after overdue.

Default notification scope:

* Notify for Open risks.
* Do not notify for Closed risks.
* Draft risk notification behaviour is configurable.
* Do not notify for completed or cancelled Risk Response Actions.
* If no owner exists, notify configured fallback recipients such as Register Admins.

Recipients are configurable per notification rule.

Default recipients:

* Risk Owner for risk review reminders.
* Risk Response Owner for Risk Response Action review reminders.

Additional recipient options:

* Register Admins
* Specific users
* Specific email addresses
* Custom Person Picker fields
* Escalation recipients after X days overdue

Notification channels:

1. In-app notifications.
2. Email notifications if SMTP is configured.

SMTP configuration is system-wide and includes host, port, authentication, from address, and TLS/SSL settings. SMTP credentials must be encrypted at rest. The system should provide a test email function and log email attempts, failures, and retries.

## 12. Permissions

### 12.1 Permission Model

Permissions are additive. A user receives the highest effective permission available through system-level, register-level, direct, or derived ownership permissions.

Explicit deny rules are not in scope unless added later.

### 12.2 System Admin

Assigned at system level. Can manage everything, including all registers, risks, Risk Response Actions, users, authentication, SMTP settings, audit logs, templates, and hard delete controls.

### 12.3 Register Admin

Assigned at register level. Can manage a specific register, including configuration, register-level permissions, risks, Risk Response Actions, register audit logs, and all records in that register.

Register Admins cannot assign or remove System Admin rights. The system should prevent removal of the last Register Admin unless a System Admin performs or confirms the action.

### 12.4 Risk Owner

Derived from the Risk Owner field on a risk.

Risk Owners can:

* See risks assigned to them.
* Edit normal fields on assigned risks.
* Review assigned risks where reviews are enabled.
* See all Risk Response Actions linked to their risks.
* Add/link/unlink Risk Response Actions where permitted.

Risk Owners cannot directly edit calculated fields.

### 12.5 Risk Response Owner

Derived from the Risk Response Owner field on a child Risk Response Action.

Risk Response Owners can:

* See actions assigned to them.
* Update actions assigned to them.
* Review actions assigned to them where reviews are enabled.
* See limited read-only parent-risk context based on fields marked **Visible to Risk Response Owners**.

They do not automatically gain full access to the parent risk.

### 12.6 Register Viewer

Assigned at register level.

Register Viewers can view all risks in a register and view linked Risk Response Actions for those risks. They cannot edit risks, actions, or configuration.

By default, Register Viewers can see non-administrative Risk Response Action fields. System metadata, internal IDs, and sensitive administrative fields are hidden unless explicitly enabled.

## 13. Authentication and User Linking

Supported authentication methods:

1. Local authentication.
2. SAML authentication, including providers such as Microsoft Entra ID.

Person assignment is based on email address. If a person is entered before they exist as a user, the email address is stored and later links automatically when that email becomes associated with a local or external-auth user.

## 14. Audit and Logging

Audit is required at four levels:

1. System Audit Log
2. Register Audit Log
3. Risk Audit Log
4. Risk Response Audit Log

All audit logs must follow a consistent structure:

* **Who:** username, user ID, client IP address, authentication method where useful, and potentially user agent/session ID.
* **When:** timestamp, stored in UTC and displayed according to user/system settings.
* **What:** action, object type, object ID/name, field changed, previous value, new value, and summary.
* **Where:** register, risk, Risk Response Action, admin/configuration area, or module as applicable.

Audit logs must be immutable, searchable/filterable, and exportable by authorised users. Audit logging should be treated as a first-class product capability rather than a later retrofit. Implementations should use a structured audit model that can support system, register, risk, and risk response audit views without losing field-level changes, review evidence, permission changes, security events, or deletion snapshots.

Search/filter fields should include actor, object type, action, date range, register, risk, Risk Response Action, and client IP.

### 14.1 System Audit Log

Captures system-level changes such as users, roles, authentication, SMTP, global templates, and system settings.

### 14.2 Register Audit Log

Captures register-level changes such as register creation, configuration changes, field changes, formulas, matrix changes, review rules, notification rules, permissions, template changes, and hard deletion of risks.

Hard delete audit entries must preserve a full last-known snapshot including core fields, custom field values, review history summaries, linked actions where applicable, actor, timestamp, client IP where captured, and optional deletion reason.

### 14.3 Risk Audit Log

Captures risk-level changes, review events, state changes, linked action changes, before/after values, actor, timestamp, and client IP.

### 14.4 Risk Response Audit Log

Captures Risk Response Action field changes, ownership changes, review events, status changes, linked risk relationship changes, before/after values, actor, timestamp, and client IP.

## 15. Core Pages

### 15.1 Home

Role-aware dashboard or overview. Detailed requirements will be developed separately.

Potential dashboard focus:

* System Admin: system health, audit activity, users, registers.
* Register Admin: overdue reviews, unassigned risks, validation issues, register summaries.
* Risk Owner: owned risks and due reviews.
* Risk Response Owner: owned actions and due reviews.
* Register Viewer: read-only summaries.

> **Note:** The implemented Home dashboard is defined in sections 8.2–8.5. Post-MVP dashboard development should refer back to the full requirements in this section.

### 15.2 Registers

Main risk register interface.

Requirements:

* Tabular risk view.
* Register switching based on access.
* Filtering, sorting, and searching.
* Open individual risks.
* Highlight validation issues.
* Exclude closed risks by default.
* Include closed risks through filters.
* Respect field visibility rules.

### 15.3 Risk Responses / My Actions

Main screen for Risk Response Actions.

Purpose:

* Show Risk Response Owners what they own.
* Help action owners update and review their actions.
* Let Register Admins/System Admins view actions across relevant registers.

Requirements:

* Filtering, sorting, and searching.
* Due date and overdue indicators.
* Review status indicators.
* Linked risks.
* Owner, status, and state information.

### 15.4 Configuration

Register configuration area for Register Admins.

Must support configuration of fields, visibility, validation, likelihood/impact, formulas, matrix, levels, inherent/residual mode, response strategy, response action mode, reviews, notifications, import/export, Created Date override, and configuration publishing.

### 15.5 Admin

System-wide administration area.

Must support users, system roles, authentication, SAML, SMTP, global templates, system audit logs, and global settings.

## 16. Import and Export

### 16.1 Risk Import

Risk import uses CSV and follows a validate-preview-commit flow.

The import process must:

* Use current register configuration.
* Support column mapping.
* Show errors and warnings before commit.
* Block hard errors.
* Require acknowledgement of warnings.
* Support Created Date override for authorised users.
* Import custom fields and owner fields where possible.

Default behaviours:

* Duplicate Risk ID: block unless update/merge mode is selected.
* Missing Risk Owner: follow register validation.
* Invalid dropdown value: block unless mapped.
* Invalid date: block until corrected.
* Missing required/custom field: follow field validation.
* Unknown person email: allow if valid email format and link later.
* Calculated field supplied: ignore imported value and recalculate.

### 16.2 Risk Export

Risk export uses CSV and must respect permissions, filtering, and field visibility rules.

### 16.3 Risk Response Import/Export

In child record mode, import/export should support separate structures for:

* Risks
* Risk Response Actions
* Risk-to-Response links

This may be implemented as staged CSV import/export.

### 16.4 CSV Template Generation

The system must generate CSV templates from the current register configuration, including applicable core fields, custom fields, headers, date formats, dropdown values where practical, and person picker fields.

### 16.5 Register Configuration Import/Export

Register configuration should be importable/exportable as JSON.

Configuration JSON should include field definitions, field order, validation rules, formulas, likelihood/impact values, matrix, risk levels, review settings, notification settings, response strategy values, and response action configuration.

Permissions may be excluded or optionally included; this remains a design decision.

## 17. Templates and Configuration Versioning

Shared register configurations are implemented as versioned templates.

Rules:

* New registers can be created from a template.
* Future template updates do not automatically alter existing registers.
* Register Admins must explicitly apply or migrate to a newer template version.
* System Admins can manage global templates.
* Register Admins can export/import configurations for registers they administer.
* Register Admins may create register-local templates if permitted by system configuration.

## 18. Reporting

Closed risks are excluded by default from operational dashboards and standard reports but can be included by authorised users.

Reporting should support the product goal of transparency and ownership by showing what is owned, due, overdue, incomplete, invalid, or concentrated by level/register.

Detailed reporting requirements will be developed separately.

## 19. Non-Functional Requirements

### 19.1 Usability

The app must be easy for non-risk specialists to use. End users should not need to understand the configuration model to update, review, or manage assigned risks and actions.

### 19.2 Security

The app must consistently enforce system-level, register-level, ownership-derived, and field visibility permissions.

### 19.3 Auditability

Audit logs must be reliable, immutable, searchable, exportable, and sufficiently detailed for governance and investigation.

### 19.4 Data Integrity

Calculated fields are protected from direct editing. Configuration changes must avoid accidental data loss and require migration/impact analysis where appropriate.

### 19.5 Flexibility

Registers must support different risk methodologies, scoring approaches, review rules, ownership models, and response action structures without code changes.
