# Observability

This document covers logging, health checks, and metrics for customRisk deployments.

## Structured Application Logging

### Log Format

The `app` container writes structured JSON logs to stdout. Each line is a valid JSON object containing the request context, operation details, and outcome.

Example log line:
```json
{"level":30,"time":1719028800000,"pid":42,"hostname":"container-id","requestId":"req-abc123","correlationId":"corr-xyz789","traceId":"trace-001","method":"PATCH","route":"registers/:registerId","statusCode":200,"duration":145,"message":"HTTP request completed"}
```

Local development mode (when `NODE_ENV=development`) automatically pretty-prints logs for readability.

### Tailing Logs

#### Application logs

```bash
docker compose logs -f app
```

This streams application logs as they occur. Press `Ctrl+C` to stop.

#### PostgreSQL logs

```bash
docker compose logs -f db
```

This streams database server logs. Useful for diagnosing connection issues, slow queries, or replication errors.

#### Both containers

```bash
docker compose logs -f
```

Interleaves both app and db logs with container labels for clarity.

### Reading JSON Logs Locally

For readability, pipe application logs through `jq`:

```bash
docker compose logs -f app | jq .
```

This pretty-prints each JSON object and adds syntax highlighting. Use `jq` filters to search specific fields:

```bash
# Find all error-level logs
docker compose logs app | jq 'select(.level == 50)'

# Find logs for a specific request
docker compose logs app | jq 'select(.requestId == "req-abc123")'

# Extract just message and duration
docker compose logs app | jq '{message, duration}'
```

## Controlling Log Verbosity

### LOG_LEVEL Environment Variable

The `LOG_LEVEL` environment variable controls which log messages appear. Valid values:

- **`error`** — only fatal and error-level messages. Minimal noise; use only when severely constrained on log volume.
- **`warn`** — errors and warnings. Recommended only for very stable production systems where issues are rare.
- **`info`** — errors, warnings, and informational messages (HTTP request completion, auth events, startup/shutdown, client validation errors). **Recommended for production.**
- **`debug`** — all messages including service-level mutations, 404s, and verbose operational detail. Disabled by default in production to reduce noise; enable only during incident investigation.

### Recommended Production Default

Set `LOG_LEVEL=info` in your deployment's `.env` file. This balances operational visibility with signal-to-noise ratio:

- Captures HTTP request lifecycle (method, route, duration, status)
- Records authentication events (login, logout, token revocation)
- Logs application startup and shutdown
- Includes all errors and validation failures
- Omits debug-level noise (per-query details, 404 discovery, verbose framework chatter)

### Setting LOG_LEVEL

#### In `.env`

```bash
LOG_LEVEL=info
```

Then start the application normally:

```bash
docker compose up
```

#### Inline Override (temporary investigation)

For a one-off debug session without editing `.env`:

```bash
LOG_LEVEL=debug docker compose up
```

This overrides the `.env` setting for the current run. **Remember to stop and restart normally when done** so production does not remain at debug level.

#### Elevating Verbosity in a Running Deployment

Currently, changing `LOG_LEVEL` requires a container restart. If your deployment supports it:

```bash
LOG_LEVEL=debug docker compose up -d
```

(Stop and restart the app service)

Then revert:

```bash
LOG_LEVEL=info docker compose up -d
```

Future work may support dynamic log level adjustment without restart via an endpoint or signal handler.

## Correlation IDs and Tracing

Every request and background operation includes correlation fields for cross-request tracing:

- **`requestId`** — unique per HTTP request, generated by the server if not supplied. Use this to link multiple logs within a single user action.
- **`correlationId`** — optional, supplied by the caller or inherited from an upstream request. Use this to trace a logical flow across multiple services or deployments.
- **`traceId`** — optional W3C trace identifier for distributed tracing. Present if the caller sends a valid `traceparent` header.
- **`jobName`** — name of a background job (e.g. `notifications_dispatch`, `import_run`).
- **`jobId`** — unique per job invocation. Use with `jobName` to filter all logs for a specific background operation.

Example: diagnosing a user-reported issue with a specific config publish:

```bash
# Find the request in logs
docker compose logs app | jq 'select(.message | contains("Published"))'

# Extract the requestId
REQUEST_ID="req-abc123"

# Find all logs for that request
docker compose logs app | jq "select(.requestId == \"$REQUEST_ID\")"
```

## Health and Metrics Endpoints

### Health Status

```bash
curl http://localhost:3000/api/v1/health
```

Returns JSON with application and database health:

```json
{
  "status": "healthy",
  "uptime": 3600,
  "database": {
    "status": "connected",
    "latency": 2
  }
}
```

### Prometheus Metrics

```bash
curl http://localhost:3000/api/v1/metrics
```

Returns plaintext Prometheus-format metrics:

- request totals by method, route template, and status code
- request error totals for `4xx` and `5xx` responses
- request duration histograms by method and route template
- process uptime

Route labels intentionally use route templates (e.g. `registers/:registerId`) or `unmatched` rather than raw URLs, so sensitive IDs, emails, query strings, and business data do not appear in metrics.

## Production Log Aggregation

In production, do not configure application-side log aggregation. Instead:

1. **Capture container stdout** — customRisk writes logs to stdout; Docker captures them via the container runtime.
2. **Use a logging driver or sidecar** — configure your Docker daemon or deployment platform to pipe container logs into your chosen aggregation stack:
   - **Loki** — use a Promtail sidecar or configure Docker's logging driver
   - **CloudWatch** — use the CloudWatch logging driver
   - **Datadog** — use the Datadog agent with container log collection
   - **Splunk**, **New Relic**, etc. — similar patterns apply

3. **No log rotation at app level** — Docker's default `json-file` driver handles log file rotation automatically. If you need log persistence or custom rotation, configure the driver in your Docker daemon config or choose a logging driver that supports rotation (e.g. `awslogs`, `splunk`).

4. **Filter and transform in the aggregation layer** — if you need to drop certain log types, enrich fields, or reformat, do this in your aggregation stack's pipeline (Loki labels and relabeling, Datadog processors, etc.), not in the application.

Example: Loki with Promtail sidecar:

```yaml
# docker-compose.yml
services:
  app:
    # ... existing config ...
  
  db:
    # ... existing config ...
  
  promtail:
    image: grafana/promtail:latest
    volumes:
      - /var/lib/docker/containers:/var/lib/docker/containers:ro
      - /var/run/docker.sock:/var/run/docker.sock
    command: -config.file=/etc/promtail/promtail-config.yaml
```

## Correlation Strategy

- Every HTTP request gets a server-generated `X-Request-Id`.
- If a caller sends `X-Correlation-Id`, the app preserves it for logs and response headers after basic character validation.
- If a caller sends a valid W3C `traceparent` header, the trace ID portion is reused for the request context.
- Error responses include `error.requestId` so support teams can match user-visible failures to server logs without exposing internal stack traces.

## Background Jobs

Use the application's `runWithJobContext(...)` helper for background work that needs tracing:

- Job logs automatically include `jobName` and `jobId` fields
- Preserve correlation context from triggering request where available
- Future job types: `notifications_dispatch`, `import_run`, `webhook_delivery`

Filter job logs:

```bash
docker compose logs app | jq 'select(.jobName == "notifications_dispatch")'
```

## Logging Best Practices

- Do not log secrets, tokens, passwords, refresh tokens, or full business payloads.
- Treat request and correlation IDs as diagnostic identifiers only, not as authentication or authorization material.
- For structured fields, prefer concise, consistent names (e.g. `statusCode` not `status_code`).
- Include relevant context for each log: who (userId if applicable), what (operation, resource), when (timestamp is automatic), outcome (statusCode, error code).
